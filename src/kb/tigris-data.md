# Tigris Data 对象存储技术文档

## 概述

Tigris 是一个全球分布式的、S3 兼容的对象存储服务，具有以下特点：

- **零出口费用**：全球复制默认开启，无需额外配置
- **S3 兼容 API**：可直接替换 AWS S3
- **全球复制**：数据自动分布到全球多个区域
- **强一致性**：基于 FoundationDB 提供严格可序列化事务

| 层级 | 用途 | 特点 |
|------|------|------|
| SSD 缓存 | 热数据 | 最快响应，毫秒级 |
| FoundationDB | 元数据 + 小对象内联 | 事务性存储，强一致性 |

| 远程区域块存储 | 全球复制 | 按需拉取，零拷贝 |

## FoundationDB 集成

### 为什么选择 FoundationDB

1. **严格可序列化事务**：与 Spanner 相同的一致性保证
2. **分布式 KV 存储**：自动分片、负载均衡
3. **模拟测试**：通过模拟测试保证正确性
4. **高可用**：Apple、Snowflake 等大规模生产验证

### 键编码方案

Tigris 使用 FoundationDB 的 Tuple Layer 进行键编码：

#### 键结构
```
[前缀] [租户ID] [数据库ID] [集合ID] [索引ID] [主键值]
```

#### 键压缩
- 使用**字典编码**：将租户、数据库、集合名称映射为整数
- 存储在 `encoding` 集合中，DDL 操作时分配唯一整数
- 不可变映射，可安全缓存

#### 时间戳编码
使用**反码编码 + FoundationDB Tuple Layer** 实现时间戳的字典序与数值序一致：

```python
# FoundationDB 使用反码(One's Complement)编码
# 反码特性：绝对值越大，字节表示越小

# 时间戳 900000000  (早期) → 编码更大
# 时间戳 1600000000 (中期) → 编码中等
# 时间戳 1700000000 (晚期) → 编码更小
# 这样正向扫描时，最新版本自然排在前面
```

**Tuple Layer 整数编码**：
```
类型码范围：
0x0c-0x13: 反码编码 (8字节到1字节)
0x14:      零
0x15-0x1c: 正数编码 (1字节到8字节)
```

#### 编码转换示例

以下演示三个时间戳如何转换为 FoundationDB Tuple Layer 编码：

**原始时间戳**：
```
900000000   → 0x35A4E900 (4字节)
1600000000  → 0x5F5E1000 (4字节)
1700000000  → 0x65494800 (4字节)
```

**第一步：确定类型码**
```
4字节整数 → 类型码 = 0x14 - 4 = 0x10
```

**第二步：计算反码 (One's Complement)**
```
反码公式: ~value (按位取反)

900000000:
  原值: 0x35A4E900
  反码: 0xCA5B16FF

1600000000:
  原值: 0x5F5E1000
  反码: 0xA0A1EFFF

1700000000:
  原值: 0x65494800
  反码: 0x9AB6B7FF
```

**第三步：组合最终编码**
```
格式: [类型码] [反码字节(大端序)]

900000000:  10 CA 5B 16 FF
1600000000: 10 A0 A1 EF FF
1700000000: 10 9A B6 B7 FF
```

**第四步：字典序验证**
```
FoundationDB 按字典序排序(逐字节比较):

10 9A B6 B7 FF  ← 1700000000 (最晚，排第一)
10 A0 A1 EF FF  ← 1600000000 (中间)
10 CA 5B 16 FF  ← 900000000  (最早，排最后)

字典序: 9A < A0 < CA ✓
数值序: 1700000000 > 1600000000 > 900000000 ✓

结论: 最新时间戳编码最小，正向扫描时自然排在前面
```

**为什么反码能保证正确排序**：
```
反码特性: 原值越大，反码的高位字节越小

1700000000 (原值最大): 9A ← 最小
1600000000 (原值中等): A0 ← 中等
900000000  (原值最小): CA ← 最大

这是因为反码将数值序反转了:
原值大 → 反码小
原值小 → 反码大
```

## ValueWrapper 设计

### Proto 定义

```protobuf
message ValueWrapper {
  int32 ver = 1;            // schema 版本号
  int32 enc = 2;            // 数据编码方式
  int32 comp = 3;           // 压缩算法
  Timestamp created_at = 4; // 创建时间戳
  Timestamp updated_at = 5; // 更新时间戳
  bytes raw = 6;            // 原始用户数据
}
```

### Protobuf 线格式

```
每个字段编码为: [Tag] [Payload]
Tag = (field_number << 3) | wire_type

wire_type:
- 0: varint (int32, int64, bool)
- 2: length-delimited (string, bytes, 嵌套消息)
```

**编码示例**：
```
ver=1, enc=0, comp=0, raw="hello"

08 01                    // field 1 (ver), varint 1
10 00                    // field 2 (enc), varint 0
18 00                    // field 3 (comp), varint 0
32 05 68 65 6C 6C 6F     // field 6 (raw), 长度5, "hello"
```

### 设计优势

1. **零拷贝读取**：未设置的字段不编码
2. **在线迁移**：可随时切换压缩/编码算法
3. **元数据索引**：支持时间范围查询
4. **Schema 演化**：通过 `ver` 字段管理版本

## 事务特性

### 严格可序列化 (Strict Serializability)

**定义**：事务执行等价于某个串行顺序，且该顺序符合真实时间顺序。

```
如果事务 A 在事务 B 开始之前完成
→ 在等价串行顺序中，A 必须排在 B 之前
→ B 的读操作必须看到 A 的写入结果
```

**与普通可序列化的区别**：

| 特性 | 可序列化 (SER) | 严格可序列化 (SS) |
|------|---------------|-------------------|
| 串行等价 | ✓ | ✓ |
| 实时约束 | ✗ | ✓ |
| 时间旅行 | 允许 | 禁止 |
| 陈旧读 | 可能 | 禁止 |

### Compare-And-Set (CAS)

**定义**：原子操作，仅当当前值等于预期值时才更新。

```python
def compare_and_set(key, expected, new_value):
    """
    原子条件更新
    返回: (success, actual_value)
    """
    current = db.get(key)
    if current == expected:
        db.put(key, new_value)
        return True, new_value
    else:
        return False, current
```

**应用场景**：
- 乐观锁：更新计数器、配置
- 条件写入：只有未被修改才能更新
- 避免 lost update 问题

**Tigris 扩展**：
- S3 API 原生支持 CAS
- 无需额外锁机制
- 支持乐观并发控制

## 全球复制机制

### 复制策略

```
用户上传对象
    │
    ├─── 元数据 ───→ FoundationDB
    │                 │
    │                 ├─── 队列推送 ───→ 所有区域
    │
    └─── 数据内容 ───→ 本地块存储
                       │
                       └─── 按需拉取 ───→ 远程区域
```

### 数据库即队列

- 利用 FoundationDB 的有序性实现复制队列
- 队列条目以创建时间为键
- 无需额外消息系统（如 Kafka）

### 优势

1. **同一事务**：数据存储和队列写入原子完成
2. **简化架构**：复用 FoundationDB 运维经验
3. **自动故障转移**：区域故障时自动切换

## Append-Only 不可变架构

### 设计原则

```
每个操作都是不可变事件：
- PUT  → 创建新版本
- DELETE → 创建墓碑
- SNAPSHOT → 时间点标记
```

### 快照机制

```python
# 快照只是一个 64 位时间戳
snapshot = 1700000000000000000  # 纳秒级

# 读取快照版本的数据
# 返回 timestamp <= snapshot 的最新版本
```

**O(1) 复杂度**：
- 无需数据复制
- 无需扫描
- 只是元数据指针

### Bucket Forking（Git 式分支）

```python
# 创建快照
snapshot = create_snapshot("my-bucket")

# 从快照分叉
fork_bucket = create_fork(
    source="my-bucket",
    snapshot=snapshot
)

# 分叉桶独立写入，共享未修改的数据
put("data.txt", "new content", bucket=fork_bucket)
```

**实现原理**：
- 递归查找父桶快照
- Copy-on-Write：只在修改时复制
- 零拷贝：瞬间分叉 TB 级数据

## 相关概念

### FoundationDB Tuple Layer
- 保序编码方案
- 支持多种数据类型
- 键按字典序排序

### 反码编码 (One's Complement)
- 负数编码方式
- 绝对值越大，字节表示越小
- 保证字典序与数值序一致

### 原子性 (Atomicity)
- 操作要么全部成功，要么全部失败
- CAS 的基础保证

### 线性一致性 (Linearizability)
- 单对象操作的强一致性
- 操作即时生效的幻觉

## 与 RustFS 架构对比

### 架构哲学

| 维度 | Tigris | RustFS |
|------|--------|--------|
| **定位** | 云原生 SaaS 对象存储 | 自托管分布式对象存储 |
| **部署模式** | 托管服务，单一全球端点 | 单二进制自部署，多节点集群 |
| **开源协议** | 专有 SaaS | Apache 2.0 开源 |
| **设计灵感** | 自研 | 受 MinIO 架构启发 |

┌───────┴───────┐                           ┌───────┴───────┐

### 关键差异详解

#### 1. 元数据存储

| 特性 | Tigris | RustFS |
|------|--------|--------|
| **存储引擎** | FoundationDB (外部分布式 KV) | 本地磁盘嵌入式存储 |
| **事务支持** | 严格可序列化事务 | 读写一致性 |
| **元数据位置** | 独立元数据层 | 与数据同节点存储 |
| **Schema 演化** | 支持在线迁移 | 本地文件系统 |

**Tigris 优势**：
- FoundationDB 提供强一致性保证
- 支持 Compare-And-Set 等高级事务语义
- 元数据与数据分离，独立扩展

**RustFS 优势**：
- 无外部依赖，部署简单
- 元数据本地存储，延迟更低
- 单节点即可运行

#### 2. 多区域同步

| 特性 | Tigris | RustFS |
|------|--------|--------|
| **同步方式** | 元数据推送 + 数据按需拉取 | Bucket Replication (S3 API) |
| **一致性** | 异步复制，最终一致 | 同步/异步可选 |
| **复制粒度** | 对象级 | Bucket 级规则 |
| **冲突处理** | 无冲突 (单向写入) | 需配置冲突解决策略 |

**Tigris 复制机制**：
```
用户写入 → 元数据存入 FoundationDB
         → 元数据异步推送到所有区域
         → 数据存储到本地块存储
         → 其他区域按需拉取数据
```

**RustFS 复制机制**：
```
源 Bucket 写入 → 触发复制规则
               → 异步/同步复制到目标 Bucket
               → 支持跨集群 Site Replication
               → 元数据随对象一起复制
```

#### 2. 数据保护

| 特性 | Tigris | RustFS |
|------|--------|--------|
| **编码方式** | 块存储 + 全球复制 | Reed-Solomon 纠删码 |
| **冗余策略** | 多区域副本 | 单集群内 k+m 分片 |
| **存储效率** | 较低 (多副本) | 较高 (纠删码) |
| **恢复速度** | 跨区域拉取 | 本地并行重建 |

**Tigris 优势**：
- 全球复制提供就近访问
- 自动故障转移
- 零出口费用

**RustFS 优势**：
- 存储效率更高 (如 RS(10,4) 仅 40% 冗余)
- 本地修复速度快
- 无跨区域流量成本

#### 3. 一致性模型

| 特性 | Tigris | RustFS |
|------|--------|--------|
| **事务隔离** | 严格可序列化 | 读写一致性 |
| **并发控制** | OCC + MVCC | 乐观锁 |
| **全局顺序** | 保证 | 不保证 |

**Tigris 优势**：
- 支持全局事务
- 防止陈旧读和因果倒置
- 适合强一致性场景

**RustFS 优势**：
- 性能开销更低
- 适合最终一致性场景

#### 4. 部署与运维

| 特性 | Tigris | RustFS |
|------|--------|--------|
| **部署复杂度** | 零运维 (SaaS) | 单二进制部署 |
| **扩展方式** | 自动全球扩展 | 手动添加节点 |
| **监控** | 内置 | OpenTelemetry |
| **成本模型** | 按用量付费 | 硬件成本 |

### 联系与共同点

1. **S3 兼容**：两者都提供 S3 API 兼容层
2. **分布式设计**：都支持多节点部署
3. **数据完整性**：都支持校验和验证
4. **版本控制**：都支持对象版本管理
5. **生命周期管理**：都支持数据分层存储

### 选型建议

| 场景 | 推荐 | 原因 |
|------|------|------|
| **全球分布式应用** | Tigris | 内置全球复制，就近访问 |
| **强一致性需求** | Tigris | 严格可序列化事务 |
| **自托管/私有化** | RustFS | 开源，无外部依赖 |
| **成本敏感** | RustFS | 存储效率高，无出口费用 |
